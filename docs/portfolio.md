## Two layout concepts

|                 | Concept A: evidence first                                                                                   | Concept B: business workflow story                                                               |
| --------------- | ----------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| Opening         | Role headline, concise promise, two project cards with status and verification links                        | Illustrated operational problem → workflow → solution → outcome, then biography and project list |
| Rough structure | Header / role and audience / Stoic case study + CI/CD case study / skills with evidence / about and contact | Header / workflow story / professional context / project gallery / about and contact             |
| Reader benefit  | Hiring lead reaches code and checks in one click                                                            | Business reader sees a familiar operational problem before technical detail                      |
| Main risk       | Academic code could overshadow analyst experience                                                           | Without an approved professional case, workflow outcomes could look invented                     |

## Design selection

Choose A provisionally. J1 explicitly asks for tested integrations and delivery practices; [public deployment evidence](evidence.md) and the Stoic source can support that story today. Concept B remains valuable once Jorge supplies a permission-cleared professional example. One-click evidence access is a design hypothesis, not a measured recruiter preference.

Use a restrained Swiss hierarchy: clear type scale, generous space, descriptive link labels and readable contrast. A Sage voice explains decisions and uncertainty. Apply authority through inspectable artifacts and consistent methods; use commitment/consistency through a focused visitor path and a concrete next action. These are design choices, not guaranteed persuasion effects. Do not add testimonials or social proof without a real attributed source and permission.

## Content outline

1. Home: “Business systems and enterprise applications — APIs, automation and evidence-based delivery.” Primary action: read a case study.
2. Work: Stoic Companion and QA/production pipeline, each with problem, personal contribution, architecture, decisions, evidence and limitations.
3. Professional context: NJIT Web and Information Systems; analyst experience as student-supplied background. Add a sanitized professional case only after Jorge verifies details and disclosure permission.
4. Stoic case study: source rights, ingestion, SQL/Qdrant, retrieval comparison, citation integrity, benchmark limitations and next steps.
5. Pipeline case study: branch promotion, quality gates and dated deployment evidence with current status separated.
6. About/resume/contact: current role and degree status personally checked; GitHub contact as the public next action.

Visitor journey: home → role and promise → case study → code/check evidence → contact. Existing site is in `is373-practical-test`; this checkpoint records the content/design decision. No changes to its deployment are needed to make the research reviewable.

Planned usability check: give Peter the README without explanation; ask him to identify audience, locate one employer-to-project trace and find the next action. Record his actual words and one resulting revision. Keyboard navigation, visible focus, descriptive links, semantic headings, responsive reading and contrast require browser checks when the selected design is implemented.
